Past: how we got here

Seven stages. Open a stage for the reasoning, what failed and the evidence. "My read" marks interpretation rather than documented reasoning.

STAGE 0 · OCT 3–4 · sibling project

A Claude Skill for a researcher on a free account

Turning point: the free Claude sandbox can't reach iCloud or Hugging Face, so the tool split into a Skill plus Mac scripts. details ▾

Goal

  • File about 2,000 I.CARE photos into existing iCloud albums, with keywords and captions.

Built

  • Skill ZIP, Mac export and apply scripts, share page, four evaluation iterations, and a classification of the real 84-photo album.

Outcome

  • A working proof of concept. Its taxonomy, silver labels and 9 gold images were reused later.
Evidence: lets-plan-about-this-golden-donut.md, reef_image_test/README.md.
STAGE 1 · OCT 4 · 12:07–13:54

Config-driven CLI with a vision LLM

Turning point: categories moved into CATEGORIES.md and the source became an iCloud shared-album link. details ▾

Built

  • A shared-album client reverse-engineered from the CloudKit web API and tested live on 84 photos.
  • Claude (default) and Gemini classifiers, and three destinations: a local folder, iCloud Drive and Photos.
  • The workflow: fetch → classify → CSV review → apply.

Failed or deferred

  • No real model call (no API key). The Photos destination was only dry-run.
  • The first sign of the iCloud hidden-file problem, patched with a workaround.
STAGE 2 · OCT 4 22:48 → OCT 9 09:48

Choosing the model again

Turning point: "not SigLIP, not yet" became "SigLIP 2 plus examples" once photos moved to Google Drive and the categories became general. details ▾

Documented reasoning

  • For species codes and people's identities, an LLM is better; Roboflow needs thousands of labels.
  • For coral / sponge / diver / people, plus example folders and "improves over time", a local embedding model fits. "The requirements changed the problem."

Revised later

  • Drive for Desktop → Drive API sign-in.
  • Gradio → FastAPI + HTMX.
  • Copy → move and rename.
  • Filed photos teaching "off by default" → on.
  • Model size "400 MB" → 1.5 GB, corrected at the plan stage.
STAGE 3 · OCT 9 · 09:53–10:37

Plan, then the v0.2 build in about 24 minutes

Turning point: one planned design: storage layer, embedders, move history, CLI, web UI and Google Cloud deploy. details ▾

Process

  • Two research subagents, 7 web searches and 2 multiple-choice questions to the owner.
  • Requirements added mid-plan: the server option uses Google Drive only, and Google Cloud is preferred "to learn it".

Measured on 69 album photos (silver labels)

  • Top level (coral / sponge): 78% zero-shot → 95.7% with examples.
  • 94% of filed photos were right at confidence 0.2, with 75% sent to Review.

Not verified

  • Drive, Vertex AI and Cloud Run. The summary called the cookie "encrypted"; the review found it is only signed.
STAGE 4 · OCT 9 · 10:50–13:10

Hands-on testing and UI churn

Turning point: the owner's tests reshaped the UI about six times, and a turtle at "97% shark" led to an absolute fit check. details ▾

Owner reports → responses

  • "Categories file too complex" → a simple list plus a categories editor.
  • "Why is it not working?" → the scanner skipped .avif files.
  • "No idea what's going on" → the page refreshes itself, and a live status panel.
  • "Terrible UI"; turtle as shark → list layout and the min_fit check.
  • "Still classifying on start" → the model loads only on Sort, behind a lock.
  • "UI should be simpler" → piles and an outliner. First real-browser check.
  • Three environment errors → the root cause (iCloud-synced Desktop) fixed by moving the virtual environment.
My read: the owner asked for simplicity at 11:13. The early versions added features instead (pagination, filters, tabs), and nobody looked at the UI in a browser until the sixth version.
STAGE 5 · OCT 9 · 13:16–16:38

Transparency and teaching by example

Turning point: "training" became a visible workflow: examples panel, web search, "one picture teaches one category", and a one-by-one viewer. details ▾

Built

  • Run receipts: model and revision, where it ran, tokens, FLOPs, CPU, memory and dollars.
  • Examples: upload, openly-licensed web search and "use as example". They are re-read on every Sort.
  • Move to… and Check this category; the viewer with number keys and undo.

Found and fixed while testing

  • Examples pulled 5 photos into Turtle (only 2 were turtles) → a cutoff calibrated per category.
  • A scoring formula bug → fixed; filed accuracy 93.8% → 94.1%.
Open question (flagged 15:32): auto-filed photos also teach, so a wrong automatic filing teaches the wrong thing. Not resolved.
STAGE 6 · OCT 9 · 17:14–22:04

Real taxonomy, code review and efficiency fixes

Turning point: the review found 15 + 7 bugs and 3 efficiency problems; the efficiency problems are now fixed. details ▾

What happened

  • The I.CARE CATEGORIES.md (60 categories) was converted to the simple format with visual descriptions.
  • Readiness check: a fresh install fails without a hand-written categories.json.
  • Efficiency fixes: History page at 30,000 moves 43 s → 20 ms; data written per filing 16 MB → about 0.5 KB.

Lessons: AI-assisted development

What the evidence shows. There is no hand-built baseline, so none of this proves time savings.

Where it helped

  • Speed: the approved plan became about 20 modules, 24 tests, deploy scripts and docs in about 24 minutes. Later requests took 1–13 minutes of assistant time each.
  • Exploration: the CloudKit album API was worked out and tested live in minutes. The plan's fact checks caught a wrong model size before any code.
  • Measuring: accuracy on 69 real photos, before/after tables for scoring fixes, and a benchmark for the efficiency fixes.
  • Tests: 0 → 60. They caught same-second undo records and a batching bug.
  • Docs: the README was updated in most feature turns.

Where it created friction

  • UI rework: about 6 versions of the main screen; 3 followed "terrible", "simpler" or "lots of issues".
  • Claims ahead of checks: an "encrypted" cookie that isn't; Drive, Cloud and installer steps documented but never run.
  • Late defects: one review at the end found 15 + 7 bugs and 3 efficiency problems.
  • Workaround before root cause: the iCloud environment problem cost four more messages before the real fix.
  • Hard to review: 259 shell calls against 13 direct file edits and writes, with no git diffs; one patch script failed on a stale anchor.
  • Scope growth: a 1,103-line web app; the owner had to ask for "DRY and KISS".

Can't conclude yet, so measure from now on

  • Faster than by hand? No baseline. Measure: lead time per request, from message to a verified result.
  • Usable by a researcher? Nobody has tried. Measure: time to the first sorted photo; target under 15 minutes.
  • Accurate on real data? Silver labels only. Measure: accuracy on a gold set, per release.
  • How much rework? Measure: "broken" or "not what I meant" follow-ups per feature, and review findings per change.
